# Customer — CSO → CCO → sub-skills

The customer function, parallel to `marketing/`. The CCO sits under the CSO as a second department head. Neither layer does the work; they triage, classify, and route.

```
orchestrator
  └── cso              (Chief Strategy Officer, top parent)        marketing/cso.md
        ├── cmo        (Chief Marketing Officer)                   marketing/cmo.md
        └── cco        (Chief Customer Officer, customer parent)   customer/cco.md
              └── triage_agent                                     customer/triage_agent.md
```

- **`cco.md`** — customer parent. Takes a customer job, sends every inbound message through the triage agent, then reports what the person wants, which head owns it, and whether a person must be involved before any reply. It never answers, sends, or decides money.
- **`triage_agent.md`** — first CCO sub-agent. Reads one message from a chatbot, contact form, or inbox and writes the analysis onto the customer record. It never replies and never sends.
- **sub-skills** — `role: subagent`, `parent: cco`. Future customer skills join the CCO automatically.

## Who owns what

| Request type | Owner |
|---|---|
| New business | `cso` |
| Support | `cco` |
| Billing or money | the user (`owner`) |
| Partnership or press | `cmo` |
| Spam | `cco` (no reply) |
| Unclear | the user (`owner`), human required |

The mapping is deterministic in code (`netlify/functions/_lib/cco-triage-core.mjs`), not a model judgement. The model classifies the request; the code assigns the owner.

## Sending

The CCO never sends. Anything that needs to leave the system goes through the CMO and its `email_writer`, after the user confirms. Triage has no send path at all.

## Adding a customer skill

Any `.md` file dropped into this folder with frontmatter `role: subagent` automatically becomes a CCO sub-skill.

1. Write the skill file here with `name`, `title`, `role: subagent`, and `parent: cco`.
2. Rebuild the CCO's route list:

   ```powershell
   .\scripts\index-customer-subagents.ps1
   ```

The script finds the customer parent (the file with `role: parent` **and** a `parent:`), collects every `role: subagent` name in this folder, and rewrites the parent's `sub_agents:` block. New skills are appended automatically — the registry is generated, not hand-edited.

## Frontmatter contract

| Field | Used by | Meaning |
|---|---|---|
| `name` | all | Stable id the parent routes by. |
| `title` | all | Human-readable name. |
| `role` | all | `parent` or `subagent`. |
| `parent` | nested parents and sub-skills | Id of the layer above. `cso` for the CCO, `cco` for its sub-skills. |
| `sub_agents` | parents | Ordered list of children. Generated by the script for the CCO. |

## Runtime

The triage agent's server-side implementation lives in the TatoIQ site:

- `tatoiq/netlify/functions/cco-triage.mjs` — public endpoint at `/api/cco/triage`
- `tatoiq/netlify/functions/_lib/cco-triage-core.mjs` — model call, validation, owner mapping, record write
- `tatoiq/docs/CCO-TRIAGE.md` — request/response, security, environment, and deploy steps

The model key stays in the Netlify function environment. The browser never sees it. Records live in Netlify Blobs, not Firebase.
